\section{Data Collection and Preprocessing}\label{sec:data}
The project uses two kinds of data.
The first is the market data that OpenTrading reads while it answers a user.
The second is the set of questions, with their correct answers, used to evaluate it.

\subsection{Market Data}\label{sec:market-data}
OpenTrading does not store market data itself.
It reads the data through opentrading-mcp, a server built by the group that exposes \num{175} tools through the Model Context Protocol.
%% Evidence: E12.
Behind these tools are public sources and providers that require an account key: price and index data of the Vietnamese exchanges through the vnstock library, financial statements from Vietstock, global indices and commodities from Yahoo Finance, crypto-assets from Binance, macroeconomic series from FRED and the World Bank, and news events from GDELT.
\todo{Confirm with the supervisor the licence wording for each provider before the server is described as public.}
Gathering many providers behind one server means that every harness sees the same data in the same form, which is also what makes the comparison in \cref{sec:validation} possible.

The providers disagree on units, periods and dates, so the server cleans the data before a model reads it.
Four rules apply to every result.
First, each result states the units of its numbers.
This rule came from a real error: one provider gives Vietnamese share prices in thousands of đồng and another in đồng, and an early version of OpenTrading reported a price 1,000 times too small.
Second, reporting periods are always given in the same order, and trading days follow the calendar of the Vietnamese market; the server never invents a date for a day without trading.
Third, missing data is reported as missing, with a reason and whether a retry may help, rather than filled with an estimate.
Fourth, tools that compute statistics over a basket of today's listed companies warn that companies which left the market are not included, a bias known as survivorship bias.

\subsection{Evaluation Data}\label{sec:evaluation-data}
Live market data changes every few seconds, so a benchmark that read it would give a different correct answer on each run.
The benchmark therefore uses a frozen snapshot.
For each task, the data that the tools would return was recorded once, with 1 November 2026 as the snapshot date and the trading session of 30 October 2026 as the last session.
During a trial the harness calls the same tools, but the answers come from the recording.
The correct answer of each task was computed from the recorded data by a script, so it is correct with respect to the snapshot; it does not certify the original filings.
The financial statements added for version 4.7 were checked against every earlier recording of the same companies and periods: all 112 shared values matched.

The tasks are questions in Vietnamese, written as a user of the product would ask them, with a required answer format.
They fall into six groups, shown in \cref{tab:taskset}.

\subsection{Selection of Tasks}\label{sec:task-selection}
The task set was built from the previous version of the benchmark.
In the earlier study (run or16), many tasks, mostly lookups and simple calculations, were answered correctly by every arm in every run.
Such tasks cannot show a difference between harnesses, so 120 of them were removed by a fixed rule: a task was removed if every arm answered it correctly in both earlier runs.
Eight of the removed tasks were refusal tasks, where the correct answer is that the data does not exist, and they were put back because a false answer to them is a serious error in a financial product.
New groups were then added to reach 200 main tasks: harder calculations on financial statements, memory tasks on financial conventions, and the investor and recommendation groups.
The removal rule was written after the earlier results were known.
It is therefore reported as an amendment (\cref{tab:amendments}).
The rule was applied to all arms alike, so it does not favour one harness, but it makes the remaining tasks harder than the earlier set.

\subsection{Grounding Rules in the System Prompt}\label{sec:grounding-rules}
The system prompt is the first algorithm of a harness: it sets the rules that the model applies at every step.
The prompt of OpenTrading puts its rules in a fixed order of priority.
Core rules come first, then the working rules of the system, then the user's own request, so that a user cannot ask the model to break a core rule.
Two core rules target the main risk of a financial assistant, which is a confident answer with a wrong number.
First, every figure on prices, volumes, financial statements or the economy must come from a tool result in the same conversation; when data is missing, the model must say which part is missing instead of estimating it or using a figure it remembers.
Second, the model may not calculate in its head: every ratio, percentage or growth rate is computed by a tool, so that the arithmetic can be checked and repeated.
Views on the future must be given as scenarios, each with its assumptions, the conditions that would prove it wrong and a likelihood.

The prompt is assembled from blocks rather than written as one text.
A line that describes a tool is included only when that tool is available, and the machine profile, used when another program rather than a person reads the answer, replaces the guidance on style with a strict answer format.
In the first request of the benchmark tasks, the system prompt of the machine profile therefore ranged from 917 to \num{1645} words, depending on the tools and features of the task.
%% Evidence: E22.
The prompt has been written in English since November 2026, because the same rules take fewer tokens in English than in Vietnamese; the Vietnamese words that users type are kept where they decide which skill or tool is chosen.

\subsection{Tool Search}\label{sec:tool-search}
With 175 data tools and the harness's own tools, sending every tool definition in every request would take a large share of the model's context and would make the model choose among many similar tools.
OpenTrading therefore defers some tools: the model receives only their names, and it loads a tool through a search tool when it needs it, as \cref{alg:tool-search} shows.
In the default mode, rarely used local tools are always deferred, and all deferrable tools are deferred once there are more than 40 tools or once their definitions would take more than 10\% of the model's context.
Sub-agents, which run short focused tasks, receive their tools directly.
\begin{algorithm}[htb]
  \caption{Ranking of deferred tools for a search query}\label{alg:tool-search}
  \begin{algorithmic}[1]
    \Require query $q$; deferred tools $D$, each with name, search hint, description and parameter names
    \Ensure tools of $D$ ordered by relevance to $q$
    \If{$q$ has the form \texttt{select:}$a,b,\dots$} \State \Return the tools named $a,b,\dots$ \EndIf
    \State $W \gets$ words of $q$ with Vietnamese diacritics removed; words marked \texttt{+} are required
    \State add to $W$ the English terms of every Vietnamese market phrase found in $q$, longest phrase first
    \For{each tool $d \in D$}
      \State $s_d \gets \sum_{w \in W}$ ( 12 if $w$ is a word of the name, else 6 if it is part of one;
      \Statex \hspace{\algorithmicindent}\hspace{\algorithmicindent} $+4$ if in the search hint; $+2$ if in the description; $+2$ if a parameter name )
      \If{a required word scores 0 for $d$} \State discard $d$ \EndIf
    \EndFor
    \State \Return tools with $s_d>0$, by decreasing $s_d$, then by name
  \end{algorithmic}
\end{algorithm}
The weights favour the name of a tool because data servers name their tools by function, such as \texttt{vn\_quote\_history}.
The table of Vietnamese phrases lets a question such as \enquote{lịch sử giá} (price history) find tools that are described in English.
Partial matches are allowed only for words of three letters or more, because short Vietnamese words would otherwise match half of the catalogue.
The benchmark of \cref{sec:validation} switches tool search off for every arm, so its results do not measure this feature.

\subsection{Validation of Tool Inputs}\label{sec:input-validation}
A model sometimes calls a data tool with an argument that the tool does not accept, for example a period written in the wrong form.
If the server then returns no data, the model may conclude that the data does not exist and report it as missing, which is a false answer.
In its grounded mode, OpenTrading checks every argument of a data tool against the schema that the server declares, before the call is sent.
An invalid call is not executed; the model receives the reason, and an explicit statement that a rejected input is not evidence that the data is missing, so it corrects the call instead of giving up.
A stricter optional policy, which also traces each reported figure back to the tool result it came from, exists for automated use; in the version 4.7 benchmark only the input check was enabled.

\section{Model Configuration and Validation}\label{sec:validation}
The project does not train a model.
Configuration therefore means choosing the LLM and the settings under which each harness runs it, and validation means testing whether the harness, not the model, changes the quality of the answers.
The group validated OpenTrading with a controlled benchmark, opentrading-benchmark, which compares it with two general-purpose coding harnesses on the same financial questions.
This section describes the design of the current study, version 4.7; its results are reported in \cref{sec:results}.

\subsection{Comparison Design}\label{sec:comparison-design}
The benchmark asks one question: given the same model, the same data and the same limits, does a harness built for financial analysis answer more questions correctly than a general-purpose one?
Three harnesses, called arms, were compared: OpenTrading in its non-interactive machine profile, OpenCode and DeepSeek Harness (DSH).
Everything except the harness was held fixed, as \cref{tab:bench-config} summarises.
All three arms used the same LLM, reached the same frozen copy of the market data through the same MCP server, and answered the same tasks under the same limits.
Each arm kept its own system prompt and tool design, since these are what a harness contributes.
Each task was run twice per arm, so that the stability of an answer could be measured as well as its correctness.

\subsection{Fairness Between the Arms}\label{sec:fairness}
A comparison between harnesses is only meaningful if no arm is given an advantage outside its own design.
The group took four measures.
First, every arm saw the same data tools; OpenTrading's extra local tools were removed and its tool search was switched off, so the benchmark does not measure those features.
Second, every arm calculated with its own shell, but every command ran in the same isolated sandbox, which replaced an earlier command filter that followed OpenTrading's own rules and so favoured it.
Third, the clock seen by every harness was set to the date of the data snapshot, so that no arm could confuse the snapshot with live data.
Fourth, questions that a harness normally asks its user were answered automatically in the same way for every arm.
The limits on requests and tokens were enforced by a shared gateway between the harnesses and the model provider, not by the harnesses themselves.

\subsection{Reproducibility}\label{sec:reproducibility}
Before the main run, the code of the benchmark, the task set and the configuration were sealed: the seal records a hash for each protected file, and a run whose files differ from the seal is refused.
The versions of the three harnesses and of their toolchains were pinned in the same way.
The holdout set was not run, and it will not be described as unseen data, because its answers are stored in a public repository.
A change made during the run is recorded as a dated amendment before it takes effect.
One such amendment, on 25 November 2026, split the second repetition of 121 tasks into a separate stream with the same code, model and limits, to finish the run within the available time.

\subsection{Scoring and the Judge}\label{sec:scoring}
A trial counts as correct only if four conditions hold.
An LLM judge must accept the final answer as correct against the gold answer.
Every number in the answer must lie within the tolerance of the gold value.
On a task whose correct answer is a refusal, because the data does not exist, the answer must not contain a number.
Finally, a manual review may reject a trial that the judge accepted, but it may never accept one that the judge rejected.
Tasks on investment recommendations and investor scenarios have a fixed rule, written before any return was computed, and are scored by that rule alone.
A trial that gives no final answer, for example because it reached a limit, counts as incorrect.
The judge was Claude Haiku 5.5, used at temperature 0.
Before the run, the group checked it on 200 controlled items: answers known to be correct, and copies of the same answers altered to be wrong in value, scale or refusal.
The judge classified all 200 items as expected (Cohen's $\kappa = 1.0$).
This check shows that the judge separates clearly correct from clearly wrong answers; it does not measure borderline cases such as partly correct answers, which remain a limitation.

\section{Evaluation Metrics}\label{sec:metrics}
The primary metric is the share of trials answered correctly, reported for each arm, for each task group and overall.
For an arm $a$ and a set of tasks $T$,
\begin{equation}\label{eq:accuracy}
  \hat{p}_a=\frac{1}{R\,|T|}\sum_{t\in T}\sum_{r=1}^{R} y_{a,t,r},
\end{equation}
where $R=2$ is the number of runs, $|T|$ is the number of tasks, and $y_{a,t,r}$ is 1 when run $r$ of task $t$ in arm $a$ is correct under \cref{sec:scoring} and 0 otherwise.
Every scheduled trial stays in the denominator, including trials that ended without an answer.

Three secondary metrics complete the picture.
Stability is the number of tasks that an arm answered correctly in both runs.
On refusal tasks, a false positive is an answer that gives a number where none exists; on answerable tasks, a false refusal is a refusal where an answer exists.
Cost is reported as the number of model requests, the number of tokens and the amount paid; these are reported separately and never added to correctness as one score.

The difference between OpenTrading and each other arm is $\Delta_b=\hat{p}_{\mathrm{OT}}-\hat{p}_b$.
Its uncertainty is estimated with a paired bootstrap over tasks: tasks are drawn with replacement \num{2000} times, both arms keep their own trials on each drawn task, and the 2.5th and 97.5th percentiles of the resulting differences form a 95\% CI.
Resampling tasks rather than trials keeps the two runs of a task together, because they are not independent.
A difference is described as a difference only when its interval excludes zero, and the word significant is not used without a test.
