\chapter{Methodology}\label{ch:methodology}

\section{Research Questions and Objectives}\label{sec:rq}
The objectives in \cref{sec:objective} are turned here into three research questions (RQs).
Each RQ states what is measured and where it is answered, so that \cref{sec:rq-answers} can answer them one by one.
\begin{description}
  \item[RQ1.~] Which parts must a harness add around a language model so that its financial analysis stays grounded in tool data, follows the constraints that the investor has stated and keeps actions under the user's control?
  The parts are the rules of \cref{sec:algorithm}, checked by automated tests (\cref{sec:testing}); the benchmark measures the first two aims through its reliability measures (\cref{sec:metrics}) and its memory group (\cref{sec:validation}).
  \item[RQ2.~] How should a market-data server return its results so that the agent knows the unit, the source and the availability of each figure?
  The measure is whether every tool of the data server replies in one shape that states whether the data is available and where and when it was taken.
  A contract check calls the tools of the server with live data and checks this shape, and a test checks that each tool on a list of tools returning prices or amounts of money states its units.
  The answer is given in \cref{sec:tool-exposure}.
  \item[RQ3.~] With the same model and the same data, does OpenTrading answer more financial tasks correctly than two general-purpose harnesses, OpenCode and DeepSeek Harness, and at what cost?
  The measures are accuracy with confidence intervals, a sign test on paired results for the same tasks, and the time and cost of each trial (\cref{sec:metrics}).
  The answer is given in \cref{sec:results}.
\end{description}
RQ1 is the main question, as it matches the objective with the largest weight; RQ3 checks what tests cannot, whether the rules improve the answers.
The harness is judged on whether its figures and conclusions match the data, not on market returns.

\section{Data Collection and Preprocessing}\label{sec:data}
OpenTrading does not store market data itself.
It reads the data through MCP (\cref{sec:project-overview}) from the group's data server \enquote{opentrading-mcp}, which offers \num{175} tools \parencite{group2026opentradingmcp}.
%% Evidence: E12.
The data comes from the following sources: prices and indices of the Vietnamese exchanges through the free tier of the \enquote{vnstock} library, financial statements from \enquote{Vietstock} through a paid API key, global indices and commodities from \enquote{Yahoo Finance}, market data from \enquote{DNSE}, crypto-assets from \enquote{Binance}, macroeconomic series from \enquote{FRED} and the \enquote{World Bank}, and news events from \enquote{GDELT}.

The providers disagree on units, periods and dates, so the data is cleaned by four rules before the model reads it:
\begin{enumerate}
  \item Results of price tools state the units of their numbers, where the units have been checked.
  One provider gives Vietnamese share prices in thousands of đồng and another in đồng, and an early version of OpenTrading labelled a price in thousands of đồng as đồng, a reading \num{1000} times too small.
%% Evidence: E64.
  \item Reporting periods are given in one order, from oldest to newest, and a price bar without a date is dropped, so no date is invented.
  \item Missing data is reported as missing, with a reason, rather than filled with an estimate.
  \item Statistics of sector cycles, which are computed over today's listed companies, warn that companies which left the market are not included, a bias known as survivorship bias.
\end{enumerate}

\label{sec:agent-loop}
OpenTrading handles each user message in one turn.
During a turn the model reasons, calls tools and reads their results, a pattern known as ReAct \parencite{yao2023react}.
One step of a turn is one request to the model together with the tool calls it makes.
The basic loop comes from a library \parencite{vercelndloop}; the group added the rules shown in \cref{alg:turn}.

By default the main agent has no limit on steps, because a research question may need many tool calls.
Three rules keep it from going round in circles.
When four steps in a row contain failed calls and no successful one, the model is reminded of the failures, on the model interfaces that accept such reminders; after eight such steps, the tools are switched off for a step, so the model has to answer with what it has.
When the model makes the same call with the same arguments three times in a row, the user is asked whether to go on.
A data server whose connection fails three times in a row is not called for a minute, after which one call tests it; a failed tool or a timeout does not count, because it comes from a server that still works.
%% Evidence: E25, E26, E69.
These thresholds of four, eight and three are not user settings; they can be changed only in OpenTrading's own test runner, which is separate from the benchmark of \cref{sec:validation} and records when each of them fires.
In a small sweep on free models, the models gave up after at most three failed steps and an earlier reminder did not change their answers, so the thresholds were kept.
%% Evidence: E69.

\begin{algorithm}[H]
  \caption{One turn of the agent loop}\label{alg:turn}
  \begin{algorithmic}[1]
    \Require message $m$; history $H$; tools; optional cap on steps or requests
    \Ensure an answer, or a statement that there is none
    \Repeat
      \Repeat \Comment{one pass is one step}
        \State \textbf{if} eight steps in a row have failed, or the cap is nearly reached \textbf{then} forbid tool calls
        \State send $H$, $m$ and the work so far to the model
        \State run the tool calls it makes, through the permission gate
      \Until{the model stops calling tools, or the cap is reached}
      \State $g \gets$ verdict of the stop gate on the last step
      \State \textbf{if} $g$ is \textsc{continue} \textbf{then} remove the broken text (a cut answer is kept) and add an instruction
    \Until{$g$ is \textsc{accept} or \textsc{give up}, or the cap is reached}
    \State \Return the answer, or a statement that there is none
  \end{algorithmic}
\end{algorithm}

A model that stops calling tools has not always answered, and the stop gate looks for such endings.
In one run recorded during development, a small model wrote a price-to-earnings ratio and a revenue under a source line although no tool had run.
The stop gate consists of rules in code and asks no second model, so accepting an answer costs no extra request.
Its ten cases fall into four groups, shown in \cref{tab:stop-gate}.

\begin{table}[H]
  \centering

  \begin{tabularx}{\textwidth}{@{}l L L@{}}
    \toprule
    {Group} & {Sign in the last step} & {The model is asked to}\\
    \midrule
    Broken call & a malformed tool call; a call written as text & make the call again, or answer\\
    \addlinespace[2pt]

A turn may be sent back at most twice in total, whatever the cases.
If a tool has already returned something to answer from, an empty answer has an extra allowance of up to three in total, so a turn has at most five recoveries.
If the text is still empty or only a repeat after that, the user is told that there is no answer.
Any other answer is kept, with a warning if its figures are unsupported.
The gate checks the form of an answer, not its truth.

\label{sec:grounding-rules}
The system prompt sets the grounding rules and the other rules that the model applies at every step, and OpenTrading puts them in a fixed order of priority.
Core rules come first, then the working rules of the system, then the user's own request, and after it the default presentation, the investor profile, the active skill and memory.
This order is an instruction in the prompt, not a check in the code: the prompt tells the model that a request of the user does not override a core rule.
Two rules target the main risk of a financial assistant, a confident answer with a wrong number \parencite{kang2023deficiency}.
First, every figure on prices, volumes, financial statements or the economy must come from a tool result in the same conversation; when data is missing, the model must say which part is missing instead of estimating it or using a figure it remembers.
Second, a working rule tells the model not to calculate in its head but to run each calculation in the shell, as explained below.
Views on the future must be given as scenarios, each with its assumptions, the conditions that would prove it wrong and a likelihood.

The prompt is assembled from blocks rather than written as one text.
Lines about some tools, such as the shell, are included only when that tool is available.
The machine profile, used when another program rather than a person reads the answer, drops the guidance on style and follows the answer format that the calling program gives.

\label{sec:figure-tracing}
A financial answer cannot be trusted if its figures do not come from the data, so figure tracing compares the figures of an answer with the numbers that the model has read.
A figure is traced if it equals one of these numbers after a change of scale and after rounding.
Suppose that a tool returned a price-to-earnings ratio of 12.34.
An answer of 12.3 is traced, because the difference of 0.04 is below 0.05, half a unit of the last digit; an answer of 12.4 is not.

In general, a figure $x$ written with $d$ decimals is traced when
\begin{equation}\label{eq:tracing}
  \min_{s\in S,\;k\in K}\bigl|\,k\,|s|-x\,\bigr|\;\le\;\tfrac{1}{2}\cdot 10^{-d},
  \qquad K=\{1,10^{\pm2},10^{\pm3},10^{\pm6},10^{\pm9}\}.
\end{equation}
Here $S$ is the set of numbers in the question, the memory notes and skills in use, the tool results and the earlier messages, and $K$ holds the scales for percentages, thousands, millions and billions.
A figure that can be read in two ways, such as 16.800 in Vietnamese and in English notation, is traced if either reading is; amounts in \enquote{nghìn tỷ} (thousand billion) are converted to billions, together with the tolerance.
Dates, whole numbers without a unit or separator, and figures marked as the model's own calculation are left out.

The result is used carefully, because a false alarm can spoil a correct answer.
If no tool ran, untraced figures can make the stop gate send the answer back (\cref{tab:stop-gate}); if tools ran, they are only recorded.
The harness thus cannot guarantee that every figure is correct: a figure may match by chance, and a correct figure may be used wrongly.
%% Evidence: E27.

Calculation by program is the next rule: LLMs make arithmetic mistakes even when their reasoning is right, and leaving the calculation to a program reduces them \parencite{gao2023pal}.
The system prompt therefore asks the model to send calculations to the shell, the computer's command line.
A command that contains only arithmetic normally runs without asking the user; it may use numbers, operators, a few mathematical functions and its own variables, but no files, loops or other programs.
Since the model can still mistype an input, the harness looks for the typed numbers, apart from common constants, in what the model has read and can remind it of those it cannot find.
On some model interfaces this reminder is not sent.
%% Evidence: E25, E27.

\label{sec:tool-search}
Tool search is needed because, with \num{175} data tools and the harness's own tools, sending every definition in every request would take a large share of the model's context and would make the model choose among many similar tools \parencite{qin2024toolllm}.
OpenTrading therefore defers some tools: the model receives only their names, and it loads a tool through a search tool when it needs it, as \cref{alg:tool-search} shows.
In the default mode, rarely used local tools are always deferred, and all deferrable tools are deferred once there are more than 40 tools or once their definitions would take more than \qty{10}{\percent} of the model's context.
For sub-agents the rarely used local tools are not deferred, but the limits of 40 tools and \qty{10}{\percent} of the context still apply.

\begin{algorithm}[H]
  \caption{Ranking of deferred tools for a search query}\label{alg:tool-search}
  \begin{algorithmic}[1]
    \Require query $q$; deferred tools $D$, each with name, search hint, description and parameter names
    \Ensure tools of $D$ ordered by relevance to $q$
    \If{$q$ has the form \texttt{select:}$a,b,\dots$} \State \Return the tools named $a,b,\dots$ \EndIf
    \State $W \gets$ words of $q$ with Vietnamese diacritics removed; words marked \texttt{+} are required
    \State add to $W$ the English terms of every Vietnamese market phrase found in $q$, longest phrase first
    \For{each tool $d \in D$}
      \State $s_d \gets \sum_{w \in W}$ ( 12 if $w$ is a word of the name, else 6 if it is part of one;
      \Statex \hspace{\algorithmicindent}\hspace{\algorithmicindent} $+4$ if in the search hint; $+2$ if in the description; $+2$ if a parameter name )
      \If{a required word scores 0 for $d$} \State discard $d$ \EndIf
    \EndFor
    \State \Return at most 5 tools (by default) with $s_d>0$ and $s_d \ge \tfrac{1}{2}\max_{e\in D} s_e$, by decreasing $s_d$, then by name
  \end{algorithmic}
\end{algorithm}

The weights favour the name of a tool because data servers name their tools by function, such as \texttt{vn\_quote\_history}.
The table of Vietnamese phrases lets a question such as \enquote{lịch sử giá} (price history) find tools that are described in English.
Partial matches are allowed only for words of three letters or more, because short Vietnamese words would otherwise match half of the catalogue.
%% Evidence: E23.

Checking tool inputs comes next: once a tool is chosen, its arguments can still be wrong, for example a period written in the wrong form \parencite{yao2024taubench}.
If the server then returns no data, the model may conclude that the data does not exist and report it as missing, which is a false answer.
The harness core has a grounded mode for automated use, which is not a user setting.
In this mode OpenTrading checks every argument of a data tool against the schema that the server declares, before the call is sent.
An invalid call is not executed; the model receives the reason, and an explicit statement that a rejected input is not evidence that the data is missing, so it corrects the call instead of giving up.
A stricter optional policy adds one round of correction and checks of the answer format.
%% Evidence: E24.

\label{sec:memory}
An assistant for investment analysis needs memory of what the investor has said across sessions: their rules, such as not trading on margin, their view on a subject and the lessons they have drawn.
The model keeps nothing from one session to the next, so the harness has to supply this text again.
Several systems in the literature let the agent write its own memory, from tiers of memory paged like an operating system \parencite{packer2023memgpt} to stored experiences and reflections \parencite{park2023generative,shinn2023reflexion} and notes that the agent links itself \parencite{xu2025amem}; surveys separate working from long-term memory \parencite{sumers2024cognitive,zhang2025survey}.
OpenTrading makes the opposite choice: only the user can make a memory entry take effect, and the model can only propose one.
A rule in memory steers the answers that follow, so if the agent could write memory, text from a web page, a tool result or a sub-agent could become a rule.
A suggestion card that quotes the user proves only that the user typed the quoted words, not that a rule worded by the model is theirs.
The paths by which entries are written and read are described in \cref{fig:memory-flow}; the rules behind them follow here.

\Cref{tab:memory-kinds} lists the five kinds of entry.
Each kind has size limits, and the code records a reason for each limit.
Text over a limit is refused when it is saved and is never cut.

Constraints are sent on every turn of the main agent and of each sub-agent, and are never cut, so they are kept small.
A thesis line is inserted when its subject comes into focus, while the detail is read only when the model asks for it, so the line is short and the detail can be long.
A thesis has at most eight invalidation conditions, because the model checks each one in turn when it answers.
%% Evidence: E49.

Every path that sends memory to a model consults one policy table, keyed by role, which allows only what it lists.
The design uses a single allow-only table because a code review found that, with a check missing in one place, sub-agents could read earlier sessions.
The main agent can only propose constraints, presentation styles and lessons through a suggestion card, and a sub-agent only receives constraints.
Decisions have no read entry in the table, so the harness never sends them to the model: they hold the user's own reasoning and stay on the user's machine.
The index marks a thesis that is refuted or closed, so that it is not taken as still valid.

\Cref{alg:memory-turn} gives the memory steps of one turn, which run before the agent loop of \cref{alg:turn}.

\begin{algorithm}[H]
  \caption{Memory steps before the agent loop of one turn}\label{alg:memory-turn}
  \begin{algorithmic}[1]
    \Require typed message $m$; role $r$ (main agent or sub-agent); model with context size $C$ and tier $t$
    \Ensure the memory text for this turn, or a held turn
    \State read the constraints from the store, read-only, with a deadline of \qty{2}{\second}
    \State \textbf{if} the read fails \textbf{then} hold the turn, unless the user chooses to run anyway
    \State \textbf{if} identity $+$ all constraints $+ \min(\text{output limit}, \num{4096})$ tokens $\ge C$ \textbf{then} hold the turn
    \State \textbf{if} $r$ is a sub-agent \textbf{then} \Return the constraints
    \State mask the memory blocks in the history whose entries were deleted
    \State \textbf{if} the notebook is off \textbf{then} \Return the constraints
    \State $S \gets$ subjects whose ticker or alias appears in $m$ as a whole word, ignoring case and diacritics
    \State $F \gets S$ together with the subjects of the two previous typed messages
    \State $R \gets$ thesis lines of the subjects in $F$, without those already in the history at the same or a newer version
    \State place the lines of $R$ in order while they fit in \num{5} items and $\min(4 \times \text{memory budget of } t, \num{4000})$ characters; replace a line that does not fit with a pointer to it
    \State \Return the constraints, the presentation styles, the index of the session and $R$
  \end{algorithmic}
\end{algorithm}
%% Evidence: E49.

The memory budget of line 10 depends on the context size of the model: \num{1000}, \num{700} or \num{300} tokens for at least \num{200000} tokens, at least \num{64000}, or less.
An entry that does not fit is left out whole or replaced by a pointer, so nothing is cut.
%% Evidence: E49.

Edits to constraints, theses and lessons are checked against the version that the form read, so an outdated form cannot overwrite a newer one, and deletion is logical (\cref{sec:ethics}).

\label{sec:permissions}
Permissions matter because an agent that can write files and run commands can also do harm.
OpenTrading has no built-in tool that places an order, and every tool call passes a permission gate with the four modes of \cref{tab:permission-modes}.
Switchable modes \parencite{anthropicndmodes} and a second model that reviews actions \parencite{anthropic2026auto} are ideas taken from Claude Code.

\begin{table}[H]
  \centering
  \caption{Permission modes and who decides}\label{tab:permission-modes}
  \begin{tabularx}{\textwidth}{@{}l L L@{}}
    \toprule
    {Mode} & {Writing a file in the workspace} & {Shell command}\\
    \midrule
    Read only (default) & the user, every time & the user, every time\\
    Ask & the user, who may allow a folder & the user, who may allow a command\\
    \addlinespace[2pt]
    Auto & new files: allowed; others: reviewing model & simple read-only commands: allowed; others: reviewing model\\
    \addlinespace[2pt]
    Bypass & allowed & allowed\\
    \bottomrule
  \end{tabularx}
  \fignote{Note: arithmetic commands and simple folder listings are allowed in every mode. Source: OpenTrading version 0.5.1 \parencite{group2026opentrading}.}
\end{table}

Some calls go to the user in every mode: reading files that hold keys, changing protected folders, writing outside the workspace, and making the same call three times in a row.
The user may allow a key file or a repeated call for the whole session, and the session's temporary folder is exempt.
For shell commands this check reads only the text of the command, so it can miss some cases.
When no user is present, a call that needs approval is refused.

In the auto mode the reviewing model sees the user's messages and the agent's actions but not the results of tools, because text planted in web pages or data could otherwise persuade it \parencite{greshake2023injection}, although reports of background agents can still reach it.
By default it is told to block an order or a transfer of money even if the user asks for it, and after three blocks in a row, or when it gives no answer, the user decides.

The reviewing model makes mistakes.
\textcite{anthropic2026auto} reported that the reviewing model of their own product missed \qty{17}{\percent} of 52 real actions that went beyond the request; this rate cannot be assumed for OpenTrading.
%% Evidence: E28.

\label{sec:multi-agent}
Sub-agents exist because a long task fills the context of a single agent with intermediate data.
The main agent can hand part of the task to a sub-agent.
The sub-agent does not see the conversation; it receives a form with the purpose, the known facts and the questions, and returns a report.
It cannot start further sub-agents, and many types of sub-agent can only read.
In this arrangement the model decides how to divide the work.

Ultradesk is a set of four multi-agent workflows for recurring tasks, in which the division of the work is written in code instead of being left to the model, following the distinction between agents and predefined workflows \parencite{anthropic2024agents}.
It resembles an orchestrator--worker system \parencite{anthropic2025multiagent}, except that its steps are fixed in code.
Its four tasks are screening, with one scorecard per company ranked in code; a fact check, with one vote per claim; a debate between bull and bear analysts with a referee, following the researchers of TradingAgents \parencite{xiao2024tradingagents}; and a sector review.
Their planned budgets range from 22 to 40 model requests in a small run and reach 276 in a large one; these are limits, not measurements.
Reports pass from one agent to the next as evidence to weigh, not as instructions, and the agents get only tools declared as read only.

Two results are computed in code.
In the screening and sector tasks, agents give each company four scores from 0 to 10, for quality, valuation, growth and financial health.
Each company's score is the mean of the four, with a criterion stressed by the user counting twice.
With more than ten companies this value is averaged with one computed from seven financial ratios.

In the fact check, a claim counts as correct or wrong only if more than half of all votes say so, and a failed vote never counts as \enquote{wrong}.
Because ultradesk may use many requests, it runs only when the user asks for it or approves it.
%% Evidence: E29.

\section{Model Configuration and Validation}\label{sec:validation}
The project does not train a model, so validation asks whether the harness, not the model, improves the answers.
For a financial assistant two qualities matter most: the answer must be correct, both in its calculation and in its conclusion, and it must arrive quickly.
These two criteria shaped the benchmark with which OpenTrading was compared with two general-purpose harnesses, OpenCode and DeepSeek Harness \parencite{group2026opentradingbenchmark}; its tasks, design and scoring are described below.

\label{sec:bench-tasks}
The benchmark holds 300 tasks, questions in Vietnamese written as a user would ask them, each with a required answer format.
They fall into the five groups of \cref{tab:taskset}, so that the result does not depend on one kind of question.
To keep the correct answers fixed, the data tools answer from a frozen snapshot recorded on 1 November 2026, with 30 October 2026 as the last trading session, and every correct answer was computed from that snapshot by a script.
Investor tasks assume a purchase at the close of 30 October 2026 and are scored with the closing prices of 23 November 2026.

\label{sec:bench-design}
Each harness was run once on all 300 tasks.
%% Evidence: E37, E45.
Each harness kept its own system prompt and tool design, since these are what a harness contributes.
The environment was set up to give no harness an advantage outside its design:
\begin{enumerate}
  \item The same model, DeepSeek V4.1 Flash with temperature 0 and no reasoning requested, answered in every harness; OpenTrading 0.5.0 with the change that allows buy and sell recommendations ran with its machine profile.
  \item Every harness saw the same data tools and a shell.   \item The clock of every harness was set to the snapshot date, so that the snapshot looked current to each harness.
  \item Questions that a harness normally asks its user, such as a request for permission, were answered automatically in the same way.
\end{enumerate}

\label{sec:bench-scoring}
A trial counts as correct only if all four conditions hold:
\begin{enumerate}
  \item The judge accepts the answer against the correct answer.
  \item Every requested number lies within the tolerance of the correct value.
  \item A task whose correct answer is a refusal, because the data does not exist, receives no number.
  \item A manual review does not reject it; the review may reject a trial but never accept one.
\end{enumerate}
Investor tasks are scored by a fixed rule on the later prices, and a trial without a final answer counts as incorrect.
Trials that failed for infrastructure reasons, such as a broken network connection, were run again, and judge replies that could not be read were judged again.
Both corrections applied the same rule to every harness and were made after the results had been seen.
The judge, Claude Haiku 5.5, graded all 900 trials.
Before the run, it was tested on 200 controlled answers, correct ones and copies made wrong in value, scale or refusal, and classified all of them as expected (Cohen's $\kappa = 1.0$).

\section{Evaluation Metrics}\label{sec:metrics}
The primary metric is accuracy, followed by a paired sign test, speed and cost, and reliability; accuracy is the share of tasks that a harness $a$ answered correctly:
\begin{equation}\label{eq:accuracy}
  \hat{p}_a=\frac{1}{|T|}\sum_{t\in T} y_{a,t},
\end{equation}
where $T$ is a set of tasks and $y_{a,t}$ is 1 when the trial of task $t$ in harness $a$ is correct under the rules of \cref{sec:bench-scoring} and 0 otherwise.
A trial that ended without an answer counts as incorrect.
Each accuracy is reported with a \qty{95}{\percent} Wilson score interval \parencite{wilson1927probable}.

Two harnesses are compared on the same tasks.
Let $w$ be the number of tasks that OpenTrading answered correctly and the other harness did not, $l$ the reverse, and $n=w+l$.
If the two harnesses were equally good, each of these $n$ tasks would be equally likely to fall either way, so the exact two-sided sign test \parencite{dixon1946sign} gives
\begin{equation}\label{eq:sign-test}
  p=\min\Bigl(1,\;2\sum_{k=0}^{\min(w,l)}\binom{n}{k}2^{-n}\Bigr).
\end{equation}
Tasks that both harnesses answered correctly, or both incorrectly, carry no information about the difference and are left out.
This is the exact form of McNemar's test, which compares two systems on the same test items through the items on which they disagree \parencite{dietterich1998approximate}.

Speed and cost are measured for every trial and reported separately, never added to accuracy as one score:
\begin{enumerate}
  \item Time per trial, from the question to the final answer, given as the median and the 90th percentile, because a few slow trials matter to a user even when the typical trial is fast.
  \item Model requests and data-tool calls per trial, which show how much work a harness needs to reach an answer.
  \item Cost, as the total over all trials and as the cost per correct answer.
\end{enumerate}
Reliability is described by the trials without an answer, false refusals of answerable tasks, numbers given where the correct answer is a refusal, and numbers outside the tolerance.

\section{Ethical Considerations}\label{sec:ethics}
OpenTrading produces analysis that a user may act on with real money, so its main ethical risks are a recommendation that is wrong or misread, the exposure of private data, and a biased comparison with other harnesses.

Since version 0.5.1, the harness may give a buy, hold or sell recommendation when a question calls for one, and the system prompt states that the user always makes the final decision.
When the user asks the model to choose, the system prompt tells it to fetch the data and give a choice within the user's risk tolerance, horizon and constraints, with the reason, the main risks and what would make it wrong.
The prompt also tells the model to say so instead of picking when data is missing or too thin, and to give no call when the user has ruled out recommendations.
A target price, a buy or sell zone or a stop-loss is derived only from tool figures of the conversation, with the method, and views on future prices are given as scenarios with a likelihood (\cref{sec:grounding-rules}).
Requests to place an order, manipulate prices, trade on inside information, spread rumours or evade regulations are refused.

These rules are instructions to a model, not guarantees, and a model may fail to follow them.
Two safeguards do not depend on the model: the harness has no built-in tool that places an order, and every tool call passes the permission gate of \cref{tab:permission-modes}.
Ten red-team questions in the evaluation set of the harness test these rules, from forced choices to an order request.
%% Evidence: E51.
The README of the harness states that it is research software, not an investment advisory service, that its answers are written by AI models and may be wrong or out of date, and that the user alone is responsible for investment decisions.

On accuracy, the grounding rules and figure tracing (\cref{sec:algorithm}) check that a figure matches the data, not that the data is right: a data provider can still supply a wrong value, so the prompt asks the model to state the date of data that may be out of date and to suggest checking the official source.

On privacy, the data of the harness, including API keys, sessions, configuration and the memory store, is stored on the user's machine in its data folder.
Where the operating system allows, only its owner can read the file of API keys.
Shell commands run by the agent receive an environment from which variables whose names mark them as keys or tokens have been removed, and reading a key file asks the user in every mode, or is refused when no user is present (\cref{sec:permissions}).
Some data does leave the machine: the question, the tool results and the memory placed in the prompt go to the model provider that the user has chosen, and data requests go to the data server.
Web searches go to DuckDuckGo or to a search service whose key the user has set, either of which can learn which tickers interest the user.
The memory store rejects text that has the form of a known key (\cref{sec:memory-flow}), and the investor's decisions are not sent to the model.

The group built both OpenTrading and the benchmark that compares it with other harnesses, which creates a risk of bias.
To limit it, the three harnesses used the same model and the same data (\cref{sec:validation}), and the results report ties and losses as well as wins (\cref{sec:accuracy}).
The memory group was designed around what OpenTrading can do, a limit noted in \cref{sec:threats}.

As for licences, the harness is released under the Apache 2.0 licence and the data server under the MIT licence.
The market data comes from the third-party sources of \cref{sec:data}, some through the free tier of a library or through keys held by the group.
The terms of each source govern how its data may be used, and the software licences give no right to the data itself; the group uses the data only for research and study.

Finally, the group used AI tools, namely Claude Code, OpenAI Codex and ChatGPT, mainly to write and fix code.
