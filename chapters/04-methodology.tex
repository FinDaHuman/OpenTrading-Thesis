\chapter{Methodology}\label{ch:methodology}

\section{Research Questions and Objectives}\label{sec:rq}
The objectives in \cref{sec:objective} are turned into three research questions (RQs), each with its measure; \cref{sec:rq-answers} answers them.
\begin{description}
  \item[RQ1.~] Which parts must a harness add around a language model so that its financial analysis stays grounded in tool data, follows the constraints that the investor has stated and keeps actions under the user's control?
  The parts are the rules of \cref{sec:algorithm}, checked by automated tests (\cref{sec:testing}); the benchmark measures the first two aims through its reliability measures (\cref{sec:metrics}) and its memory group (\cref{sec:validation}).
  \item[RQ2.~] How should a market-data server return its results so that the agent knows the unit, the source and the availability of each figure?
  The measure is whether every tool replies in one shape that states availability, source and time.
  It is checked by a contract check that calls the tools with live data and by a test of the stated units of price tools; the answer is in \cref{sec:tool-exposure,sec:rq-answers}.
  \item[RQ3.~] With the same model and the same data, does OpenTrading answer more financial tasks correctly than two general-purpose harnesses, OpenCode and DeepSeek Harness, and at what cost?
  The measures are accuracy with confidence intervals, a sign test on paired results, and time and cost (\cref{sec:metrics}); the answer is in \cref{sec:results}.
\end{description}
RQ1 is the main question, as it matches the objective with the largest weight; RQ3 checks what tests cannot, whether the rules improve the answers.
The harness is judged on whether its figures and conclusions match the data, not on market returns.

\section{Data Collection and Preprocessing}\label{sec:data}
OpenTrading does not store market data; it reads it through MCP (\cref{sec:project-overview}) from the group's data server \enquote{opentrading-mcp}, which offers \num{175} tools \parencite{group2026opentradingmcp}.
%% Evidence: E12.
The data comes from the following sources: prices and indices of the Vietnamese exchanges through the free tier of the \enquote{vnstock} library, financial statements from \enquote{Vietstock} through a paid API key, global indices and commodities from \enquote{Yahoo Finance}, market data from \enquote{DNSE}, crypto-assets from \enquote{Binance}, macroeconomic series from \enquote{FRED} and the \enquote{World Bank}, and news events from \enquote{GDELT}.

The providers disagree on units, periods and dates, so the data is cleaned by four rules before the model reads it:
\begin{enumerate}
  \item Results of price tools state the units of their numbers, where the units have been checked.
  One provider gives Vietnamese share prices in thousands of đồng and another in đồng, and an early version of OpenTrading read such a price \num{1000} times too small.
%% Evidence: E64.
  \item Reporting periods are given in one order, from oldest to newest, and a price bar without a date is dropped, so no date is invented.
  \item Missing data is reported as missing, with a reason, rather than filled with an estimate.
  \item Statistics of sector cycles warn that companies which left the market are not included (survivorship bias).
\end{enumerate}

\section{Algorithm Design}\label{sec:algorithm}
The project does not train a model, so its algorithms are the rules of the harness.
\Cref{tab:problems} lists the difficulties that these rules address, and the rules are described below in the same order.
They are grouped by concern: the agent loop and its stop gate, the grounding of figures, the choice and use of tools, memory, permissions, and work shared among several agents.
This order is not the order in which the rules act in a turn.
The memory steps run before the agent loop (\cref{alg:memory-turn}), while the permission gate and the input check run each time the model calls a tool (\cref{alg:turn}).

\label{sec:agent-loop}
OpenTrading handles each user message in one turn.
During a turn the model reasons, calls tools and reads their results, a pattern known as ReAct \parencite{yao2023react}.
One step of a turn is one request to the model together with the tool calls it makes.
The basic loop comes from a library \parencite{vercelndloop}, and the group added the rules shown in \cref{alg:turn}.

By default the main agent has no limit on steps, because a research question may need many tool calls.
Three failure limits keep a model from repeating a call that fails \parencite{qin2024toolllm}.
First, when four steps in a row contain failed calls and no successful one, the model is reminded of the failures, on the model interfaces that accept such reminders.
After eight such steps, the tools are switched off for one step, so the model has to answer with what it has.
Second, when the model makes the same call with the same arguments three times in a row, the user is asked whether to go on.
Third, a data server whose connection fails three times in a row is not called for a minute, after which one call tests it.
A failed tool or a timeout does not count towards this limit, because it comes from a server that still works.
%% Evidence: E25, E26, E69.

The thresholds of four, eight and three are not user settings.
They can be changed only in OpenTrading's own test runner, which is separate from the benchmark of \cref{sec:validation} and records when each limit fires.
The group ran a small sweep with this runner on free models, with simulated data and one run for each setting.
The models gave up after at most three failed steps in a row, so the reminder after four was never reached.
On the models that receive reminders, an earlier reminder did not change the answers.
The thresholds were therefore kept.
%% Evidence: E69.

\begin{algorithm}[H]
  \caption{One turn of the agent loop}\label{alg:turn}
  \begin{algorithmic}[1]
    \Require message $m$; history $H$; tools; optional cap on steps or requests
    \Ensure an answer, or a statement that there is none
    \Repeat
      \Repeat \Comment{one pass is one step}
        \State \textbf{if} eight steps in a row have failed, or the cap is nearly reached \textbf{then} forbid tool calls
        \State send $H$, $m$ and the work so far to the model
        \State run the tool calls it makes, through the permission gate
      \Until{the model stops calling tools, or the cap is reached}
      \State $g \gets$ verdict of the stop gate on the last step
      \State \textbf{if} $g$ is \textsc{continue} \textbf{then} remove the broken text (a cut answer is kept) and add an instruction
    \Until{$g$ is \textsc{accept} or \textsc{give up}, or the cap is reached}
    \State \Return the answer, or a statement that there is none
  \end{algorithmic}
\end{algorithm}

A model that stops calling tools has not always answered \parencite{anthropic2025harnesses}, and the stop gate looks for such endings.
In one run recorded during development, a small model wrote a price-to-earnings (P/E) ratio and a revenue under a source line although no tool had run.
The stop gate consists of rules in code and asks no second model, so accepting an answer costs no extra request.
Its ten cases fall into the four groups of \cref{tab:stop-gate}.

  \centering

    \midrule

A turn may be sent back at most twice in total, whatever the cases.
If a tool has already returned data to answer from, an empty answer is allowed up to three retries in total, so a turn has at most five recoveries.
If the answer is still empty or only a repeat after that, the user is told that there is no answer.
Any other answer is kept, with a warning if its figures are unsupported.
The gate checks the form of an answer, not its truth.

\label{sec:grounding-rules}
The system prompt sets the grounding rules in a fixed order of priority.
The core rules come first, then the working rules of the system, then the user's own request, and then the default presentation, the investor profile, the active skill and memory.
This order is an instruction to the model, not a check in the code.
Two rules target the main risk of a financial assistant, a confident answer with a wrong number \parencite{kang2023deficiency}.
First, every figure on prices, volumes, financial statements or the economy must come from a tool result in the same conversation.
When data is missing, the model must say which part is missing instead of estimating it or using a figure it remembers.
Second, a working rule tells the model not to calculate in its head but to run each calculation in the shell, as explained below.
Views on the future must be given as scenarios, each with its assumptions, the conditions that would prove it wrong and a likelihood.

The prompt is assembled from blocks, so lines about a tool appear only when that tool is available.
The machine profile, used when another program reads the answer, drops the guidance on style and follows the answer format that the program gives.

\label{sec:figure-tracing}
A financial answer cannot be trusted if its figures do not come from the data, so figure tracing compares the figures of an answer with the numbers that the model has read.
A figure is traced if it equals one of these numbers after a change of scale and after rounding.
Suppose that a tool returned a P/E ratio of 12.34.
An answer of 12.3 is traced, because the difference of 0.04 is below 0.05, half a unit of the last digit; an answer of 12.4 is not.

In general, a figure $x$ written with $d$ decimals is traced when
\begin{equation}\label{eq:tracing}
  \min_{s\in S,\;k\in K}\bigl|\,k\,|s|-x\,\bigr|\;\le\;\tfrac{1}{2}\cdot 10^{-d},
  \qquad K=\{1,10^{\pm2},10^{\pm3},10^{\pm6},10^{\pm9}\}.
\end{equation}
Here $S$ is the set of numbers in the question, the memory notes and skills in use, the tool results and the earlier messages, and $K$ holds the scales for percentages, thousands, millions and billions.
A figure that can be read in two ways, such as 16.800 in Vietnamese and in English notation, is traced if either reading is.
Dates, plain whole numbers and figures marked as the model's own calculation are left out.

Because a false alarm can spoil a correct answer, untraced figures make the stop gate send an answer back only if no tool ran (\cref{tab:stop-gate}); if tools ran, they are only recorded.
Tracing cannot guarantee that a figure is correct: a figure may match by chance, and a correct figure may be used wrongly.
%% Evidence: E27.

Calculation by program is the next rule: LLMs make arithmetic mistakes even when their reasoning is right, and leaving the calculation to a program reduces them \parencite{gao2023pal}.
The system prompt therefore asks the model to send calculations to the shell.
There, a command that contains only arithmetic (numbers, operators, a few functions and its own variables, but no files, loops or other programs) runs without asking the user.
The harness also looks for the typed numbers in what the model has read, and can remind the model of those it cannot find.
%% Evidence: E25, E27.

\label{sec:tool-search}
With \num{175} data tools and the harness's own tools, sending every definition in every request would take a large share of the model's context and make the model choose among many similar tools \parencite{qin2024toolllm}.
OpenTrading therefore defers tools once there are more than 40 of them or once their definitions would take more than \qty{10}{\percent} of the context.
The model then receives only their names and loads a tool through a search tool when it needs it.
The search ranks tools by the words of the query, giving most weight to the tool's name and translating Vietnamese market phrases into the English terms of the tool descriptions (\cref{alg:tool-search} in \cref{sec:app-code}).
%% Evidence: E23.

Once a tool is chosen, its arguments can still be wrong, for example a period written in the wrong form \parencite{yao2024taubench}, and an empty result may then be reported as missing data.
In its grounded mode for automated use, OpenTrading checks every argument of a data tool against the schema that the server declares, before the call is sent.
An invalid call is not executed, and the model is told why and that a rejected input is not evidence that the data is missing.
%% Evidence: E24.

\label{sec:memory}
An assistant for investment analysis needs memory of what the investor has said across sessions: their rules, such as not trading on margin, their view on a subject and the lessons they have drawn.
The model keeps nothing from one session to the next, so the harness has to supply this text again.
Several systems in the literature let the agent write its own memory.
They range from tiers of memory paged like an operating system \parencite{packer2023memgpt} to stored experiences and reflections \parencite{park2023generative,shinn2023reflexion} and notes that the agent links itself \parencite{xu2025amem}, and surveys separate working from long-term memory \parencite{sumers2024cognitive,zhang2025survey}.
OpenTrading makes the opposite choice: only the user can make a memory entry take effect, and the model can only propose one.
A rule in memory steers the answers that follow, so if the agent could write memory, text from a web page, a tool result or a sub-agent could become a rule.
A suggestion card that quotes the user proves only that the user typed the quoted words, not that a rule worded by the model is theirs.

\Cref{tab:memory-kinds} lists the five kinds of entry; text over a size limit is refused when it is saved, never cut.

Constraints are sent on every turn and never cut, so they are kept small; a thesis line is sent only when its subject comes into focus, and its detail only on request.
%% Evidence: E49.

Every path that sends memory to a model consults one policy table, keyed by role, which allows only what it lists.
The group chose a single allow-only table after a code review found that, with a check missing in one place, sub-agents could read earlier sessions.
Decisions have no read entry in the table, so they never reach the model.
\Cref{alg:memory-turn} gives the memory steps of one turn, which run before the agent loop of \cref{alg:turn}.

\begin{algorithm}[H]
  \caption{Memory steps before the agent loop of one turn}\label{alg:memory-turn}
  \begin{algorithmic}[1]
    \Require typed message $m$; role $r$ (main agent or sub-agent); model with context size $C$ and tier $t$
    \Ensure the memory text for this turn, or a held turn
    \State read the constraints from the store, read-only, with a deadline of \qty{2}{\second}
    \State \textbf{if} the read fails \textbf{then} hold the turn, unless the user chooses to run anyway
    \State \textbf{if} identity $+$ all constraints $+ \min(\text{output limit}, \num{4096})$ tokens $\ge C$ \textbf{then} hold the turn
    \State \textbf{if} $r$ is a sub-agent \textbf{then} \Return the constraints
    \State mask the memory blocks in the history whose entries were deleted
    \State \textbf{if} the notebook is off \textbf{then} \Return the constraints
    \State $S \gets$ subjects whose ticker or alias appears in $m$ as a whole word, ignoring case and diacritics
    \State $F \gets S$ together with the subjects of the two previous typed messages
    \State $R \gets$ thesis lines of the subjects in $F$, without those already in the history at the same or a newer version
    \State place the lines of $R$ in order while they fit in \num{5} items and $\min(4 \times \text{memory budget of } t, \num{4000})$ characters; replace a line that does not fit with a pointer to it
    \State \Return the constraints, the presentation styles, the index of the session and $R$
  \end{algorithmic}
\end{algorithm}
%% Evidence: E49.

The memory budget in line 10 of \cref{alg:memory-turn} depends on the context size of the model.
It is \num{1000}, \num{700} or \num{300} tokens for a context of at least \num{200000} tokens, at least \num{64000} tokens, or less.
An entry that does not fit is replaced by a pointer rather than cut.
Edits are checked against the version that the form read, so an outdated form cannot overwrite a newer one, and deletion is logical (\cref{sec:ethics}).

\label{sec:permissions}
Permissions matter because an agent that can write files and run commands can also do harm.
OpenTrading has no built-in tool that places an order, and every tool call passes a permission gate with the four modes of \cref{tab:permission-modes}.
Switchable modes \parencite{anthropicndmodes} and a second model that reviews actions \parencite{anthropic2026auto} are ideas taken from Claude Code.

    \midrule
    Read only (default) & the user, every time & the user, every time\\
    Ask & the user, who may allow a folder & the user, who may allow a command\\
    \addlinespace[2pt]
    Auto & new files: allowed; others: reviewing model & simple read-only commands: allowed; others: reviewing model\\
    \addlinespace[2pt]

Some calls go to the user in every mode, such as reading files that hold keys, writing outside the workspace or making the same call three times in a row.
When no user is present, a call that needs approval is refused.
In the auto mode the reviewing model sees the user's messages and the agent's actions but not tool results, so that text planted in web pages or data cannot persuade it \parencite{greshake2023injection}.
It is told to block an order or a transfer of money even if the user asks, and after three blocks in a row the user decides.
Such a reviewer makes mistakes: \textcite{anthropic2026auto} reported that theirs missed \qty{17}{\percent} of 52 real actions that went beyond the request, a rate that cannot be assumed for OpenTrading.

\label{sec:multi-agent}
A long task fills the context of a single agent with intermediate data \parencite{anthropic2025multiagent}, so the main agent can hand part of it to a sub-agent.
The sub-agent receives a form with the purpose, the known facts and the questions, returns a report and cannot start further sub-agents.
Ultradesk is a set of four multi-agent workflows for recurring tasks: screening, a fact check, a bull-and-bear debate with a referee after TradingAgents \parencite{xiao2024tradingagents}, and a sector review.
In these workflows the division of the work is written in code instead of being left to the model \parencite{anthropic2024agents}.
Their agents get only read-only tools, pass reports to each other as evidence rather than instructions, and combine scores and votes in code.
Because a run may use many requests, it starts only when the user asks for it or approves it.
%% Evidence: E29.

\section{Model Configuration and Validation}\label{sec:validation}
The project does not train a model, so validation asks whether the harness, not the model, improves the answers.
Answers are judged first by correctness and then by time and cost.
The validation is a benchmark in which OpenTrading was compared with two general-purpose harnesses, OpenCode and DeepSeek Harness \parencite{group2026opentradingbenchmark}.
Its tasks, design and scoring are described below.

\label{sec:bench-tasks}
The benchmark holds 300 tasks, questions in Vietnamese written as a user would ask them, each with a required answer format.
They fall into the five groups of \cref{tab:taskset}.
To keep the correct answers fixed, the data tools answer from a frozen snapshot recorded on 1 November 2026, with 30 October 2026 as the last trading session, and every correct answer was computed from that snapshot by a script.
Investor tasks assume a purchase at the close of 30 October 2026 and are scored with the closing prices of 23 November 2026.

\label{sec:bench-design}
Each harness was run once on all 300 tasks and kept its own system prompt and tool design, since these are what a harness contributes.

The environment was set up to give no harness an advantage outside its design:
\begin{enumerate}
  \item The same model, DeepSeek V4.1 Flash with temperature 0 and no reasoning requested, answered in every harness; OpenTrading 0.5.0 with the change that allows buy and sell recommendations ran with its machine profile.
  \item Every harness saw the same data tools and a shell.
  OpenTrading also had its tool for reading the full stored result of an earlier data call (\cref{sec:architecture}) and, in memory tasks, its read-only memory tool.
  Its tool search was off, every command ran without approval inside a sandbox, and no reminders were sent after tool results; of its grounded mode, only the input check was on (\cref{sec:tool-search}).
%% Evidence: E24, E32.
  \item The clock of every harness was set to the snapshot date, and questions that a harness normally asks its user, such as a request for permission, were answered automatically in the same way.
  \item In memory tasks, each harness received the earlier session through its own mechanism, since memory is part of what a harness contributes.
  For OpenTrading, the benchmark's controller saved each of the user's rules in the memory store through the same path as the user's form, in the user's exact words, and the notebook was on.
  OpenCode could only resume the earlier session, and DeepSeek Harness could resume it and search past sessions with its own tool.
  This setup favours OpenTrading by design, because the current version of each rule reaches its model without a search; \cref{sec:harness-difference} discusses what this means for the results.

\end{enumerate}

\label{sec:bench-scoring}
A trial counts as correct only if all four conditions hold:
\begin{enumerate}
  \item The judge accepts the answer against the correct answer.
  \item Every requested number lies within the tolerance of the correct value.
  \item A task whose correct answer is a refusal, because the data does not exist, receives no number.
  \item A manual review does not reject it; the review may reject a trial but never accept one.
\end{enumerate}
Investor tasks are scored by a fixed rule on the later prices, and a trial without a final answer counts as incorrect.
Trials that failed for infrastructure reasons, such as a broken network connection, were run again, and judge replies that could not be read were judged again.
Both corrections applied the same rule to every harness and were made after the results had been seen.
The judge, Claude Haiku 5.5, graded all 900 trials.
Before the run, it was tested on 200 controlled answers, correct ones and copies made wrong in value, scale or refusal, and it classified all of them as expected (Cohen's $\kappa = 1.0$).
%% Evidence: E17, E37, E43, E71.

\section{Evaluation Metrics}\label{sec:metrics}
The primary metric is accuracy, followed by a paired sign test, speed and cost, and reliability.
Accuracy is the share of tasks that a harness $a$ answered correctly:
\begin{equation}\label{eq:accuracy}
  \hat{p}_a=\frac{1}{|T|}\sum_{t\in T} y_{a,t},
\end{equation}
where $T$ is a set of tasks and $y_{a,t}$ is 1 when the trial of task $t$ in harness $a$ is correct under the rules of \cref{sec:bench-scoring} and 0 otherwise.
A trial that ended without an answer counts as incorrect.
Each accuracy is reported with a \qty{95}{\percent} Wilson score interval \parencite{wilson1927probable}.

Two harnesses are compared on the same tasks.
Let $w$ be the number of tasks that OpenTrading answered correctly and the other harness did not, $l$ the reverse, and $n=w+l$.
If the two harnesses were equally good, each of these $n$ tasks would be equally likely to fall either way, so the exact two-sided sign test \parencite{dixon1946sign} gives
\begin{equation}\label{eq:sign-test}
  p=\min\Bigl(1,\;2\sum_{k=0}^{\min(w,l)}\binom{n}{k}2^{-n}\Bigr).
\end{equation}
Tasks that both harnesses answered correctly, or both incorrectly, carry no information about the difference and are left out.
This is the exact form of McNemar's test, which compares two systems on the same test items through the items on which they disagree \parencite{dietterich1998approximate}.

Speed and cost are reported separately and are never added to accuracy as one score.
Time per trial is given as the median and the 90th percentile, because a few slow trials matter to a user.
Work is given as the model requests and data-tool calls per trial, and cost in total and per correct answer.
Reliability is described by the trials without an answer, false refusals of answerable tasks, numbers given where the correct answer is a refusal, and numbers outside the tolerance.

\section{Ethical Considerations}\label{sec:ethics}
OpenTrading produces analysis that a user may act on with real money, so its main ethical risks are a wrong or misread recommendation, the exposure of private data and a biased comparison with other harnesses.

The first risk is harm from a recommendation: a user may lose money by trusting a wrong call.
Since version 0.5.1 the harness may recommend buying, holding or selling, but the decision stays with the user.
The model must give the reasons, the main risks and what would prove the call wrong, and no built-in tool places orders.
Requests to manipulate prices, trade on inside information or spread rumours are refused.
The documentation states that the harness is research software, not an investment advisory service.
These safeguards rest partly on instructions that a model may not follow (\cref{sec:grounding-rules}), so they reduce the risk rather than remove it.

The same holds for figures: a figure that matches its tool result (\cref{sec:figure-tracing}) is still wrong if the source is wrong.
The model is therefore told to date figures that may be out of date and to point the user to the official source, and the user remains responsible for checking a figure before acting on it.

The second risk is the exposure of private data, such as what a person owns and plans.
Keys, sessions and memory stay on the user's machine, the user chooses the model provider, and only the user decides what memory holds; the investor's decisions are never sent to the model (\cref{sec:memory-flow}).
Deleting a memory entry is logical: the entry is cleared in the store, but backups and text already sent to a provider are out of the harness's reach, so the interface does not promise physical deletion.
The limit is that the question, the tool results and the memory placed in the prompt must still go to the chosen provider, and a web search can reveal which tickers interest the user.

The third risk is a biased comparison, because the group built both OpenTrading and the benchmark that judges it.
To limit it, the three harnesses used the same model and the same data, and the results report ties and losses as well as wins (\cref{sec:validation,sec:accuracy}).
The memory group was still designed around what OpenTrading can do, so its results favour OpenTrading, and this limit is stated with the results (\cref{sec:threats}).
